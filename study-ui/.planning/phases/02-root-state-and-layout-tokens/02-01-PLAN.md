# Plan 01: Root State And Layout Tokens

<objective>
Complete Phase 2 by splitting sidebar state semantics, exposing responsive policy datasets at the shell root, and adding token-driven layout contracts for future mobile/tablet content adaptation.
</objective>

<threat_model>
## Threat Model

### T-01: Sidebar Behavior Regression
- **Severity:** medium
- **Risk:** Splitting `isSidebarOpen` could change compact drawer visibility, desktop docked sidebar behavior, or settings-mode forced expansion.
- **Mitigation:** Keep `AppChrome` as the policy-aware router. Preserve the existing `shouldPinSidebarOpen` desktop settings behavior and update source tests.

### T-02: Token Scope Drift
- **Severity:** medium
- **Risk:** New token overrides could use inconsistent names or leak assumptions into phone/tablet-specific token families.
- **Mitigation:** Define shared token names once in `:root` and override the same names using datasets. Add `app.source.test.ts` assertions.

### T-03: Phase Scope Creep
- **Severity:** low
- **Risk:** Starting ThreadCanvas, SettingsPanel, or compact sidebar behavior work would blur later phase boundaries.
- **Mitigation:** Do not edit `ThreadCanvas.tsx`, `SettingsPanel.tsx`, `Sidebar.tsx`, or shell behavior beyond state/dataset wiring unless required by tests.
</threat_model>
