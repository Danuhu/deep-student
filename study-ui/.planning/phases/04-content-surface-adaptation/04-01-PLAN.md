# Plan 01: Content Surface Adaptation

<objective>
Complete Phase 4 by adapting `ThreadCanvas`, composer, and `SettingsPanel` to consume the shared responsive layout tokens, degrade dense settings safely under desktop width, and preserve one shared UI across phone, tablet, and desktop.
</objective>

<threat_model>
## Threat Model

### T-01: Token Contract Bypass
- **Severity:** high
- **Risk:** Replacing hard-coded values with different hard-coded responsive classes would leave the app with two layout systems.
- **Mitigation:** Source tests must assert `--workspace-max-width`, `--composer-max-width`, `--page-gutter-inline`, `--composer-bottom-offset`, and safe-area token usage.

### T-02: Composer Becomes Hard To Use On Phone
- **Severity:** high
- **Risk:** Secondary controls can crowd the input/send path or bottom safe-area can hide the composer in WebView contexts.
- **Mitigation:** Make textarea and send persistent primary controls, move secondary controls into a flexible/scrollable area, and use `--composer-bottom-offset`.

### T-03: Settings Dense Data Loses Meaning
- **Severity:** medium
- **Risk:** Removing the six-column pseudo-table without labels would make compact cards ambiguous.
- **Mitigation:** Compact fallback must use labeled `dl` rows for dimension, model, dataset, count, type, and status.

### T-04: Switch Row Accessibility Regression
- **Severity:** medium
- **Risk:** Making the whole row clickable by nesting interactive elements can create invalid or confusing semantics.
- **Mitigation:** Use a local row helper with a label area tied to the switch id and keep the Radix `Switch` as the only actual switch control.

### T-05: Desktop Shell Regression
- **Severity:** high
- **Risk:** Touching AppChrome for settings gutters could accidentally affect sidebar/titlebar/window behavior.
- **Mitigation:** Limit AppChrome edits to the settings scroll wrapper and keep AppChrome source tests focused on existing shell contracts.
</threat_model>
