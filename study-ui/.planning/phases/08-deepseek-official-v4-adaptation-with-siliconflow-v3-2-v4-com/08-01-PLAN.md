# Plan 08-01: Versioned DeepSeek Adapter Compatibility

<objective>
Implement official DeepSeek V4 support while preserving SiliconFlow DeepSeek V3.2 and future SiliconFlow V4 compatibility through one shared `DeepSeekAdapter`, explicit DeepSeek model-version profiles, and host-specific request serialization.
</objective>

<scope>
This plan updates DeepSeek adapter logic, official builtin presets, capability/default inference, settings semantics, and regression coverage. It does not add new provider adapters, live API smoke tests, Anthropic-format DeepSeek support, or a broad settings redesign.
</scope>

<threat_model>

## Assets

- User API keys and provider configs.
- Saved model IDs and existing SiliconFlow V3.2 setups.
- Chat correctness in tool-calling flows where `reasoning_content` must be preserved.
- User cost exposure from model defaults, context windows, and output token limits.

## Risks

- Sending the wrong reasoning fields can break requests or silently disable thinking.
- Dropping `reasoning_content` in tool loops can cause DeepSeek API errors or unstable agent behavior.
- Replacing legacy aliases can break saved configs for existing official DeepSeek users.
- Treating 384K max output as a default can create unexpected cost spikes.
- Coupling UI toggles to model capability can corrupt provider/model metadata.

## Mitigations

- Keep one adapter with isolated model-version and host-protocol helpers.
- Preserve legacy aliases and existing saved IDs.
- Test official V4, SiliconFlow V3.2, and SiliconFlow V4-shaped IDs separately.
- Keep conservative output defaults while representing large context/output values as capabilities.
- Verify `reasoning_content` capture/passback behavior remains unchanged for streaming and tool calls.
- Do not log API keys or send live provider calls during automated tests.

</threat_model>
